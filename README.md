# task-manager

Самый лучший менеджер задач

Проект ведётся согласно модели github flow.

## Как работать с репой

1. Создаём issue с той фичой, которую должны реализовать.

- Ишью попадает в карточку backlog. Если прямо сейчас реализовать
  не готовы, то там и оставьте. Если готовы, то переводите в ready,
  но это не принципиально.

2. Реализуем фичу в своей отдельной ветке, в чужие не лезем.
3. Создаём PR. Что там указывать написано в правилах.
4. В PR указываем assignee - себя. В качестве reviewer - своего любимого
   члена команды. Не забудьте указать issue, которую закрываете.

- issue можно указать с помощью синтаксиса "closes #номер" в описании PR.
  Не нужно эти номера где-то смотреть, гитхаб всё подскажет.
- если не любите такой способ, можно это сделать вручную, после создания PR.

5. Дальше ревьюер ревьюит. Если все согласны, а мы все согласны, то вливаем.
   Вливайте со сквошем. Там есть такая опция. Но на самом деле пофигу.

- Всё merge конфликты разрешает asignee сам. reviewer этим не занимается.

## Правила

- Прямые коммиты в основную ветку запрещены. Все изменения попадают в неё через
  pull/merge request.
- Каждый pull request должен быть просмотрен и одобрен минимум одним другим
  участником команды.
- Каждый участник команды должен выступить и автором, и ревьюером. Распределение
  вклада проверяется по истории репозитория.
- В описании pull request указываются идентификаторы требований FS и разделов HLD,
  которые он реализует.

## Definition of Done

- код влит в основную ветку через pull request с одобрением;
- реализованы все требования FS, указанные в карточке;
- проект собирается, приложение запускается;
- изменения не ломают ранее реализованную функциональность.
